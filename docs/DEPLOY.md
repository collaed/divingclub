# Production deploy — procedure & runbook

Production is **`prod.clubcep.eu`** — Hetzner, app at `/opt/deploy/apps/divingclub-prod`,
served by `php8.3-fpm` (Caddy → `php8.3-fpm-prod.sock`), Redis queues via Horizon
(`supervisor` program `horizon-prod`). Staging is `/opt/deploy/apps/divingclub`
(`horizon`), auto-deploy suspended since 2026-09-05.

> `php` (the default CLI) on the box is **PHP 8.5 without `mbstring`/`bcmath`/`intl`** —
> it CANNOT boot Laravel. Every deploy/cron/maintenance command must use
> **`/usr/bin/php8.3`** explicitly, or `sudo -u clubcep php8.3 …`.

## Golden rules

1. **Never commit `bootstrap/cache/*.php`.** They are generated by
   `artisan package:discover` and are environment-specific. `.gitignore` is the
   stock Laravel `*` / `!.gitignore`. A committed manifest that references a
   provider no longer in `vendor/` bricks the whole app (see incident below).
2. **Clear before rebuild:** `rm -f bootstrap/cache/packages.php bootstrap/cache/services.php`
   *before* `php8.3 artisan package:discover`. A stale manifest stops artisan
   from booting, so you cannot even run `package:discover` to fix it.
3. **Config is intentionally NOT cached** on prod (`config:cache` has bitten us).
   `optimize:clear` only.
4. **Prove health before restarting Horizon.** `curl` `/health`; HTTP 200 or 299
   (the app's own "degraded" code) is acceptable, anything else means roll back.
5. **CI green first** — `lint`, `test`, `build` all passing on the commit.

## Normal deploy

```bash
# 0. CI green on main; DB snapshot
ssh prod.clubcep.eu 'sudo -u postgres pg_dump divingclub_prod | gzip > /mnt/data/prod/backup/pre-deploy-$(date +%Y%m%d-%H%M%S).sql.gz'

# 1. run the hardened script (identical to deploy/auto-deploy.sh in the repo)
ssh prod.clubcep.eu '/opt/deploy/auto-deploy.sh'
```

The script pulls `origin/main`, `composer install --no-dev`, wipes + rebuilds the
package cache under `php8.3`, `migrate --force`, `optimize:clear`, health-gates,
then restarts `horizon-prod`. On any failure it `git reset --hard` to the previous
commit, rebuilds caches, restarts Horizon, and exits non-zero.

## Manual deploy (script unavailable)

```bash
ssh prod.clubcep.eu
cd /opt/deploy/apps/divingclub-prod
BEFORE=$(sudo -u clubcep git rev-parse HEAD)          # note this for rollback
sudo -u clubcep git fetch origin main && sudo -u clubcep git reset --hard origin/main
sudo -u clubcep php8.3 /usr/local/bin/composer install --no-dev --optimize-autoloader
sudo -u clubcep rm -f bootstrap/cache/packages.php bootstrap/cache/services.php
sudo -u clubcep php8.3 artisan package:discover
sudo -u clubcep php8.3 artisan migrate --force
sudo -u clubcep php8.3 artisan optimize:clear
curl -sS -m20 -o /dev/null -w '%{http_code}\n' https://prod.clubcep.eu/health   # want 200 or 299
sudo supervisorctl restart horizon-prod
```

Rollback: `sudo -u clubcep git reset --hard $BEFORE`, then repeat composer /
`rm -f bootstrap/cache/*.php` / `package:discover` / `optimize:clear` / restart.

## Migrations that new code depends on

`git reset --hard` puts the new code live **before** `migrate` runs. For a
code-only change that window is harmless. But when new code hard-references a
column/table the migration is about to add (a new global middleware, a query
with `whereNotNull('new_col')`, …), requests in that ~10 s gap hit
`column "x" does not exist` and 500.

- For such deploys, wrap the risky steps: `sudo -u clubcep php8.3 artisan down`
  before `git reset`, `... artisan up` after `optimize:clear`. Members see the
  maintenance page for ~15 s instead of intermittent 500s.
- Middleware/listeners that write "nice to have" data (e.g. `TrackActivity`)
  must catch their own DB errors so this gap degrades silently — but that does
  not cover controller queries, hence `artisan down`.
- Seen on 2026-09-08 (`#51`): 4× `last_seen_at does not exist` at 16:22:49,
  self-cleared once `migrate` finished.

## Runbook — "every route returns 500, error page won't render"

Symptom in `storage/logs/laravel-*.log`:
`Class "…\ServiceProvider" not found` at `RegisterProviders`, then
`Target class [translator] does not exist`.

Cause: `bootstrap/cache/packages.php` lists a service provider not present in
`vendor/` (stale committed copy restored by `git checkout`, or generated by the
broken PHP 8.5). Fix:

```bash
ssh prod.clubcep.eu
cd /opt/deploy/apps/divingclub-prod
sudo -u clubcep rm -f bootstrap/cache/packages.php bootstrap/cache/services.php
sudo -u clubcep php8.3 artisan package:discover
sudo -u clubcep php8.3 artisan optimize:clear
curl -sS https://prod.clubcep.eu/health
```

## History

* **2026-09-08** — total outage. `bootstrap/cache/packages.php` was committed to
  the repo (un-ignored) with a stale `Fruitcake\LaravelDebugbar\ServiceProvider`
  entry. The nightly `git checkout -- .` restored it; on a no-op night
  `package:discover` never ran to overwrite it, so the app booted against a
  missing provider. Fixed by untracking the file + hardening this script.
* **2026-09-06** — same shape: `Failed opening required config/activity_types.php`
  from a stale cached config/manifest.
